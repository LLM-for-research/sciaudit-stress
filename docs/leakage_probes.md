# Пробы на утечку метки: §10.2, §10.3 и §5.5

Три гейта, которые проверяют не систему, а **датасет**. Вопрос у всех один:
можно ли угадать gold-вердикт, не читая evidence? Если можно, метрики на этом
срезе меряют не аудит, а что-то другое — и чем выше окажется результат участника,
тем меньше он будет значить.

| Проба | Что показывается модели | Что чинить при срабатывании |
|---|---|---|
| [`metadata_probe`](../sciaudit/leakage/metadata_probe.py) (§10.2) | тип и длина claim, число и длины единиц evidence, модальности, source_kind, `paper_id`, форма ID | убрать поле, перебалансировать классы, перегенерировать ID |
| [`claim_only_probe`](../sciaudit/leakage/claim_only_probe.py) (§10.3) | только слова claim | **балансировать случаи, а не править формулировки** |
| [`id_randomness_check`](../sciaudit/leakage/id_randomness_check.py) (§5.5) | сами идентификаторы | перегенерировать ID независимо от разметки |

## Запуск

```bash
uv run python -m sciaudit.leakage.metadata_probe \
  --inputs data_public/public_dev/inputs.jsonl \
  --gold data_public/public_dev/gold.jsonl

uv run python -m sciaudit.leakage.claim_only_probe \
  --inputs data_public/public_dev/inputs.jsonl \
  --gold data_public/public_dev/gold.jsonl

uv run python -m sciaudit.leakage.id_randomness_check \
  --inputs data_public/public_dev/inputs.jsonl \
  --gold data_public/public_dev/gold.jsonl
```

Все три гоняются в CI на обоих публичных срезах. Коды возврата одинаковые:
`0` — чисто или подозрение, `1` — утечка, `2` — ошибка использования.

## Как устроено измерение

Мануал требует «beats baselines by a meaningful margin», но не говорит, что
такое meaningful при двух десятках инстансов: разрыв в 8 пунктов — это два
инстанса. Поэтому вместо порога на разрыв используется **перестановочный тест**.

1. Проба обучается и проверяется по схеме leave-one-out: каждый инстанс по
   очереди становится тестовым, обучение идёт на остальных.
2. Метки перемешиваются, и вся процедура повторяется 500 раз.
3. p-value — доля перестановок, где случайные метки дали точность не хуже
   наблюдённой.

Это отвечает ровно на нужный вопрос: как часто такой результат получается, когда
связи нет вовсе. Заодно тест сам учитывает перекос классов — стратегия «всегда
самый частый класс» на перестановках работает так же хорошо, как на настоящих
метках, и потому не создаёт ложной тревоги.

Пороги: `p < 0.05` — утечка, гейт падает; `0.05 ≤ p < 0.20` — подозрение,
печатается и пропускает. Второй порог существует потому, что на десятках
инстансов граница между «связь есть» и «повезло» широкая, а гейт, который
краснеет на шуме, через неделю выключают.

**Пробы обязаны быть слабыми.** Дерево ограничено двумя уровнями, claim-проба —
наивный Байес. Сильная модель найдёт связь в любом тексте, и гейт превратится в
генератор ложных тревог. Ловится грубая утечка — «одно поле решает», — а не
тонкая.

## Как читать вывод

```
metadata_probe: OK: связи метки с этими признаками не видно
  инстансов: 24, классов: 4
  точность пробы (leave-one-out): 0.250
  всегда самый частый класс:      0.292
  случайный ответ по частотам:    0.260
  перестановки: медиана 0.208, максимум 0.667
  p-value: 0.4790
  дерево на всех данных (что именно оно нашло):
  evidence_len_min <= 80.5
    ...
```

Дерево печатается всегда, даже когда проба молчит: когда она однажды сработает,
штабу нужно знать, **какое поле** течёт, а не только что что-то течёт. Corollary:
`claim_only_probe` печатает слова с наибольшим перекосом по классам — если проба
сработала, это и есть список к балансировке.

## Что показали пробы на текущих данных

Оба публичных среза проходят метаданную и claim-пробу чисто:

| Срез | metadata_probe | claim_only_probe |
|---|---|---|
| `public_warmup` (17) | p = 0.68 | p = 0.86 |
| `public_dev` (24) | p = 0.48 | p = 0.72 |

Точность обеих проб **ниже**, чем у стратегии «всегда самый частый класс», —
то есть по метаданным и по одной формулировке вердикт не угадывается.

Отдельно приятно в claim-пробе: слово `all` в warm-up оказалось индикатором
`warranted`, а не `overclaimed`. Это ровно тот баланс, которого требует §10.3, —
сильная формулировка сама по себе меткой не является.

### Подозрение, которое было и закрыто

Первый прогон `id_randomness_check` на `public_dev` дал **подозрение**: если
отсортировать 24 инстанса по `instance_id`, одинаковые вердикты сбивались в
блоки — пять `warranted` подряд, соседей с одной меткой 10 при ожидании 5.3,
p = 0.021. Форма и смысл идентификаторов были при этом безупречны.

Причина оказалась ровно той, которую §5.5 и имеет в виду: идентификаторы
`public_dev` выдавались по ходу разметки, сгруппированной по вердикту.
`public_warmup`, сделанный иначе, ту же проверку проходил чисто (p = 0.34).

Лечение — то, которое мануал и предписывает: перегенерация.

```bash
uv run python -m sciaudit.construction.regenerate_ids \
  --internal data_paper_derived/*.internal_annotation.jsonl \
  --rewrite data_public/public_dev/manifest.json \
  --avoid data_public/public_warmup/inputs.jsonl examples/sample_inputs.jsonl \
  --gold data_public/public_dev/gold.jsonl
uv run python -m sciaudit.construction.derive_public \
  --internal data_paper_derived/*.internal_annotation.jsonl \
  --out-dir data_public/public_dev
```

Инструмент выдаёт новые ID из криптографического источника, переписывает ссылки
`seed_instance_id`, перемешивает порядок записей и заменяет старые ID в
манифесте. Публичные `inputs.jsonl` и `gold.jsonl` он не трогает — они выводятся
проекцией, и второго места, где собирается публичный срез, быть не должно.

После перегенерации: соседей с одной меткой 8 при ожидании 5.3, p = 0.138 —
раскладка неотличима от случайной.

### Две поправки, которые нашлись по дороге

**Ложное срабатывание на счётчик.** Проверка считала счётчиком любой ID,
кончающийся тремя цифрами, — а у случайного идентификатора из 36 знаков такой
хвост бывает примерно в двух процентах случаев. Сразу после перегенерации гейт
упал на честных `sas_76r7y392` и `sas_zelmt770`. Теперь ловится то, что и
описано в §5.5: разделитель, за которым идут одни цифры до конца
(`sas_seed_00045`, `sas_00000123`).

**Неудачный жребий.** Первая же перегенерация случайно дала раскладку хуже
исходной (p = 0.006): при двадцати четырёх инстансах так складывается примерно
раз на полторы сотни попыток. Такая выдача ничего не сообщает о разметке, но
выглядит как та, что сообщает, и роняла бы гейт вечно. Поэтому инструмент сам
проверяет полученную раскладку тем же тестом и при подозрительной бросает жребий
заново. Это не подгонка под тест: отбрасывается случайное совпадение, а не
информация, — источник случайности меток не видит вовсе.
