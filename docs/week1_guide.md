# Гид первой недели

Добро пожаловать. Этот гид проводит от *нуля* до *первого смёрженного вклада* без единой встречи.
Если что-то здесь непонятно — это баг документации, заводите issue.

**Сначала контекст (5 минут):** пробегите [что это такое и чем не является](benchmark_framing.md).
Главное: **Спринт 1 — это Track A, минимальный контролируемый срез, а не финальный бенчмарк.** Вы
помогаете построить рельсу, а затем нагрузить её.

---

## 1. С чего начать

Что нужно заранее: `git`, Python ≥ 3.11 и [uv](https://docs.astral.sh/uv/) (наш пакетный
менеджер — `pip` напрямую мы **не** используем).

```bash
# 1. забрать репозиторий
git clone <central-repo-url> sciaudit-stress
cd sciaudit-stress

# 2. создать окружение и поставить всё из локфайла
uv sync

# 3. убедиться, что рельса проходит от входа до конца
uv run pytest -q
uv run python system_template/run.py --input examples/sample_inputs.jsonl --output /tmp/preds.jsonl
uv run python -m sciaudit.baselines.b0_always_insufficient \
  --input examples/sample_inputs.jsonl --output /tmp/b0.jsonl
```

Если `pytest` зелёный и обе команды записали файл с предсказаниями — окружение верное.
Теперь прочитайте три коротких файла, чтобы понять контракт:

- `schemas/track_a_input.schema.json` — единственное, что получает система (см. [документ по схемам](schemas.md)).
- `schemas/prediction.schema.json` — единственное, что система вправе выдать.
- `sciaudit/baselines/b0_always_insufficient.py` — наименьшая полная система (B0).

**Золотое правило:** любая система, бейзлайн или ваша, подчиняется одному интерфейсу —
`--input inputs.jsonl --output predictions.jsonl`, по одной строке предсказания на строку входа.

## 2. Как выбрать issue

1. Откройте трекер и отфильтруйте по **`good first issue`** и **`track-A`**.
2. Возьмите то, что соответствует вашему уровню и **ни за кем не закреплено**.
3. **Оставьте комментарий, что берёте задачу**, до начала работы — чтобы двое не собирали одно и то же.
4. Если ничего не подходит, предложите своё: заведите issue с описанием пробела. Маленькое и
   чётко очерченное лучше большого и размытого.

Хорошие стартовые области в Track A: новые под-метрики evaluator'а, расширение проверок на утечку,
валидаторы схем, тест-кейсы, документация, превращение заглушки бейзлайна в настоящий модуль.
Следующие треки (RAG, уровень статьи, дообучение) открываются **после** baseline gate — не
начинайте с них на первой неделе.

**Правило масштаба:** один issue = один владелец, один артефакт, одно ревьюабельное изменение.
Если у задачи отросли щупальца — разделите её.

## 3. Как сделать PR

Работаем через pull request'ы с CI и ревью TA. В `main` не пушим никогда.

```bash
git checkout -b your-name/short-topic
# ... вносим изменение ...
uv run pytest -q          # должно быть зелёным локально до пуша
git add -A
git commit -m "Track A: <что сделано> (closes #<issue>)"
git push -u origin your-name/short-topic
# затем открыть PR в main
```

Ваш PR обязан:

- **быть маленьким и сфокусированным** — один issue, лёгкий для ревью;
- **проходить CI** — тесты, сканы утечки и smoke-прогоны бейзлайна и шаблона должны быть зелёными;
- **ссылаться на свой issue** (`closes #NN`);
- **не трогать приватные данные** — никогда не добавлять gold-метки, стресс-поля, скрытые входы
  или провенанс (`.gitignore` это сторожит; обходить его не надо);
- **включать заполненный** [еженедельный апдейт](weekly_update_template.md) в описание PR, в том
  числе что делала LLM и что вы проверили руками (см.
  [политику использования LLM](llm_use_policy.md)).

**Правило двух подписей:** изменение попадает в центральный репозиторий только после того, как
**один TA подтвердит схемную/техническую корректность**, а **другой — научную**. Комментарии на
ревью — это работающий процесс, а не отказ.

## 4. Как отчитываться о прогрессе

Каждую неделю выкладывайте короткий апдейт (в PR, в еженедельном треде или в канале команды) по
[шаблону](weekly_update_template.md):

- **Сделано** — что реально закончено.
- **PR / артефакт** — ссылки.
- **Блокер** — что мешает (называйте рано; блокер на второй день дёшев).
- **Следующий шаг** — одно дело, которое вы сделаете следующим.
- **Нужна помощь** — кто или что вас разблокирует.

Вместе с настоящими системами с самого начала едут два артефакта:

- [карточка системы](system_card_template.md) с описанием того, что это за система;
- строка в [реестре вкладов](contribution_ledger.md) с записью о том, что вы сделали.

## Definition of done первой недели

Неделя удалась, если вы можете:

- [ ] локально прогнать `uv run pytest`, шаблон и B0;
- [ ] объяснить разделение на две схемы и почему стресс-метаданные приватны;
- [ ] взять issue и открыть один небольшой PR (правка документации или теста тоже считается);
- [ ] выложить один еженедельный апдейт.

Это всё. Понимать каждую метрику пока не нужно — нужно уметь безопасно двигаться внутри рельс.
Глубина придёт с треками B–D.
